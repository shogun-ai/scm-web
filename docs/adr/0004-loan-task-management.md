# 0004. Зээлийн хүсэлтийн task management (судалгааны урсгалыг орлох)
Төлөв: Санал болгосон (D5, D6 — Хэрэглэгчийн батлах шаардлагатай)
Огноо: 2026-11-20

## Нөхцөл байдал
www.scm.mn-ээс ирэх зээлийн хүсэлтийг олон шаттай "зээлийн судалгаа" (LOS assessment → `LoanResearch`)-гаар биш, админы тохируулсан маягт + task (хуваарилах, төлөв, үр дүн, түүх) урсгалаар боловсруулна. Хуучин хүсэлтийн хадгалагдсан өгөгдлийг өөрчлөхгүй, migration бичихгүй. "Баримт AI уншилт" цэс өөрчлөгдөхгүй. Дэлгэрэнгүй: `docs/design/loan-task-management.md`, discovery `docs/architecture/loan-task-management-current.md`.

Шалгуур (жин): аюулгүй байдал/эрхийн регрессгүй (30), хуучин өгөгдөл хөндөхгүй (25), хэрэгжүүлэх хугацаа (20), буцаах боломж (15), засвар үйлчилгээ (10).

## Авч үзсэн хувилбарууд ба шийдвэр

### D1. Task өгөгдлийг хаана хадгалах
| Хувилбар | Аюулгүй (30) | Өгөгдөл (25) | Хугацаа (20) | Буцаах (15) | Засвар (10) | Нийт |
|---|---|---|---|---|---|---|
| A. `LoanRequest`-д шинэ `task*` талбар (`Schema.add`) | 27 | 22 | 18 | 14 | 7 | **88** |
| B. Тусдаа `LoanTask` collection (`requestId` ref) | 22 | 25 | 10 | 14 | 7 | 78 |
**Шийдвэр: A.** Нэг query-гээр scope/жагсаалт, одоогийн queue/хамгаалалт шууд ашиглагдана. B нь хуучин баримтад огт хүрэхгүй давуутай ч 2 collection-ийн join, давхар scope, давхар эрхийн логик шаардана. A-ийн эрсдэл (default материалжих)-ийг "шинэ талбарт default байхгүй, массив `default: undefined`" дүрэм ба тестээр хаана.

### D2. Шинэ маягтын бичлэгийн `intakeVersion`
| Хувилбар | Давуу | Сул |
|---|---|---|
| A. `intakeVersion:'quick-v1'` + `formVersion:'task-v1'` | `server.js`/`loanIntake.js`-ийн 8 газрын `quick-v1` хамгаалалт (scope, legacy PUT allow-list, research холбоос) автоматаар үйлчилнэ; server.js өөрчлөлт бага | "quick-v1" нэр утгаараа нарийн биш |
| B. `intakeVersion:'task-v1'` + бүх шалгалтыг `isScopedIntake()` болгох | Цэвэр утга | 8 газар засах; нэгийг ч алгасвал legacy route-оор ямар ч нэвтэрсэн хэрэглэгч хандах эрхийн цоорхой |
**Шийдвэр: A.** Аюулгүй байдлын регрессийн эрсдэлийг 0 болгоно. Ирээдүйд B руу тусдаа refactor-оор шилжиж болно.

### D3. Бүтээгдэхүүн / дэд бүтээгдэхүүний эх үүсвэр
| Хувилбар | Давуу | Сул |
|---|---|---|
| A. `LOAN_PRODUCTS` (код) хэвээр + `LoanFormConfig` бүтээгдэхүүн бүрт 1 баримт, дэд бүтээгдэхүүн embedded | Хамгийн бага; одоогийн validation, ProductContent, queue-ийн нэрс эвдрэхгүй; config нэг баримт = атомар хадгалалт, version | Шинэ бүтээгдэхүүн нэмэхэд код өөрчлөх |
| B. DB product catalog, `ProductContent`/`LOAN_PRODUCTS`/frontend жагсаалтуудыг нэгтгэх | Нэг эх сурвалж | L хөдөлмөр, public сайт, CMS, chatbot, LOS бүгдэд нөлөө |
**Шийдвэр: A.** Шаардлагад "admin дэд бүтээгдэхүүн үүсгэнэ" гэсэн; үндсэн бүтээгдэхүүн нэмэх шаардлага алга (YAGNI). Frontend-ийн хатуу жагсаалтуудыг (`PRODUCT_IDS`, `LoanRequestQueue.PRODUCTS`) нэгтгэх нь тусдаа жижиг ажил.

### D4. Статус
**Шийдвэр:** тусдаа `taskStatus` (6 утга) + `taskStatus` байхгүй үед хуучин 13 статусаас уншихдаа derive (design §4.2). Хуучин `status`, `workflowRevision`-ийг шинэ endpoint бичихгүй; конкурент хамгаалалт шинэ `taskRevision`. Хуучин `resolved` = "нөхцөлтэй зөвшөөрсөн" → `resolved` + outcome `approved_conditional`; хуучин string-ийг шинэ label-д хэзээ ч шууд ашиглахгүй. Татгалзсан хувилбар: хуучин `status`-ийг шинэ утгаар дахин ашиглах (утгын давхцал, хуучин UI эвдрэх, өгөгдөл өөрчлөх).

### D5. Хуваарилалтын талбар — **Хэрэглэгчийн батлах шаардлагатай**
| Хувилбар | Давуу | Сул |
|---|---|---|
| A. Одоогийн `assignee{userId,name}`-ийг шинэчлэх (хуучин бичлэгт ч) | Scope/legacy хамгаалалт нэг эх сурвалжтай; одоогийн `PATCH /api/loan-requests/:id` аль хэдийн үүнийг бичдэг workflow талбар | Хуучин бичлэгийн нэг талбар өөрчлөгдөнө (харилцагчийн өгөгдөл биш) |
| B. Шинэ `taskAssignee` + effective assignee | Хуучин талбар огт хөндөгдөхгүй | `requestScope`, `canAccessRequest`, server.js middleware-ийг өөрчлөх (`$or` scope), хуучин хариуцагч legacy route-оор хандах эрх үлдэх эрсдэл; +M хөдөлмөр |
**Шийдвэр (санал): A.** Хариуцагч нь хадгалагдсан хүсэлтийн мэдээлэл биш, ажлын урсгалын төлөв. Хэрэглэгч татгалзвал B.

### D6. AI автомат (`runPostSubmissionAutomation`) task-v1-д — **Хэрэглэгчийн батлах шаардлагатай**
**Шийдвэр (санал):** default унтраалттай (`LOAN_TASKS_AI_AUTOMATION=true` үед л). Шалтгаан: "энэ урсгалд зээлийн судалгаа байхгүй"; OpenAI руу PII/баримт илгээх, зардал багасна. "Баримт AI уншилт" цэс ажилтан гараар ашиглахад хэвээр.

### D7. Rollout flag
**Шийдвэр:** backend env `LOAN_TASKS_ENABLED` (Render, frontend redeploy шаардлагагүй) + бүтээгдэхүүн бүрийн `isActive`. Frontend нь P1-ийн `enabled`-ээр хуучин QuickLoanRequest / LoanOrigination руу автоматаар буцна. Татгалзсан: `VITE_*` build flag (Vercel redeploy шаардана).

### D8. Имэйл
**Шийдвэр:** `nodemailer` + itools SMTP, process доторх background (`setImmediate`), queue/retry-гүй, хэзээ ч throw хийхгүй, `MAIL_ENABLED`+SMTP env дутуу бол чимээгүй унтраалттай. Татгалзсан: Resend/SendGrid API (шинэ гэрээ/DNS), Mongo-д суурилсан queue + cron (YAGNI; Phase 2 retry болж болно).

## Үр дагавар
Эерэг: server.js-д ~10 мөрийн өөрчлөлт; хуучин хамгаалалт бүрэн дахин ашиглагдана; хуучин өгөгдөл хөндөгдөхгүй (D5-аас бусад); 3 түвшний rollback (бүтээгдэхүүн, flag, revert) өгөгдлийн rollback-гүй.
Сөрөг: `quick-v1` нэр утга алдагдана; task-v1 бичлэгийн хуучин `status` царцах тул хуучин dashboard тоо зөрнө; шинэ бүтээгдэхүүн нэмэхэд код хэрэгтэй.
Эрсдэл: `trust proxy` тохируулаагүйгээс public limiter бүх зочинд нэг сав байж болзошгүй (одоогийн quick-д ч мөн) — devops шалгах; Mongoose default материалжих (тестээр хаасан); `$or` scope дарагдах (`$and` дүрэм).
